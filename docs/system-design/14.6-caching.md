# 14.6 System Design: Multi-Tier Caching

```mermaid
flowchart LR
    Client[Browser] -->|1. Browser Cache (Static Assets)| CDN[2. Edge CDN (Cloudflare)]
    CDN -->|3. Cache Miss| App[Node.js Express App]
    App <-->|4. Redis Cache (Session & User Object Cache-Aside)| Redis[("Redis Cluster")]
    App -->|5. DB Read on Cache Miss| DB[("MongoDB Primary")]
```

---

## 1. What It Is in Plain Words
Caching is the architectural technique of storing frequently requested, high-cost data in high-speed, temporary storage (typically RAM or edge servers) so that future requests can be served in sub-milliseconds without recalculating or querying the primary database.

---

## 2. Whether and How THIS Project Uses It
In the current codebase, caching is **Partially Used**:
- **Static Assets**: Browser caching is leveraged by Express's `express.static` module for `public/` files.
- **Session Caching**: Not explicitly isolated in RAM; `connect-mongo` queries MongoDB disk directly for session data on every authenticated request.
- **Application Data**: No Redis cache is currently deployed.

---

## 3. Caching Strategies & Comparison Table

| Cache Strategy | How It Works | Consistency Risk | Read Latency | Write Latency | Fit for This Auth Portal |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Cache-Aside (Lazy Loading)**| App queries cache; on miss, reads DB and populates cache | Low (Invalidate on write) | Sub-millisecond on hit | Standard DB write | **Optimal for user profile hydration** |
| **Read-Through** | App treats cache as primary; cache handles DB read | Low | Fast | Standard | Complex cache wrapper setup |
| **Write-Through** | App writes to cache, which synchronously writes to DB | Zero (Always consistent) | Fast | Higher (Two synchronous writes) | Good for mission-critical session updates |
| **Write-Behind (Write-Back)** | App writes to cache; cache batches async writes to DB | High (Data loss on crash) | Fastest | Fastest | Dangerous for clinical authentication records |

---

## 4. Cache Invalidation & Thundering Herd Defense
1. **Invalidation Strategy**:
   - When an employee updates their profile: write to MongoDB, then immediately execute `redis.del('user:' + userId)` to force a fresh read on the next request.
   - When an employee logs out: execute `redis.del('session:' + sessionId)` simultaneously with the MongoDB deletion.
2. **Cache Stampede (Thundering Herd) Defense**:
   - If 1,000 clinicians access the system simultaneously during morning shift change when the cache expires, all 1,000 requests could hit MongoDB at once.
   - **Remediation**: Use **Mutex Locking** (e.g. `redlock` or a short 5-second distributed lock) so only one request queries MongoDB while the remaining 999 wait for the cache to be repopulated.

---

## 5. What Breaks First at Scale
- **10x Load**: MongoDB handles session reads without caching.
- **100x Load**: MongoDB read IOPS spike due to duplicate queries across `sessions` and `employees`.
- **1000x Load**: Database connection pool exhaustion and disk saturation.

---

## 6. Senior Engineering Improvements
Introduce a **Redis Cache Cluster** between Express and MongoDB:
1. Configure `connect-redis` as the session store adapter.
2. Cache hydrated `res.locals.user` objects in Redis with a 15-minute TTL.
3. Serve `login.html` and static font files through Cloudflare CDN with a 30-day cache header.

---

## 7. 30-Second Spoken Answer

If missed, it queries MongoDB, populates Redis, and invalidates the cache key immediately whenever the user updates their profile or logs out."
